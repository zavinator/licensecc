# Development and usage workflow

Below a description of the development and usage process. Comments and progress are reported on
[issue #42](https://github.com/open-license-manager/licensecc/issues/42)

![dev-build-process](https://user-images.githubusercontent.com/1121667/64474031-e5afff80-d1a0-11e9-9819-f3b7e4e2126d.png)

## Build release
Open License Manager developers build a new release merging code to the `master` branch. Implementing
[GitFlow](https://nvie.com/posts/a-successful-git-branching-model) this should happen only when a new
release is ready to be deployed. The build and test runs are automated with GitHub Actions (see
`.github/workflows/`).

### Binary release contents
`licensecc` does not distribute pre-compiled binaries of the library: each build generates the
signing key pair and embeds the public key into the compiled code. What a release provides is:

* license generator source/executable (`lccgen`).
* source code of the unconfigured library.
* source code of (part of) the tests.

### Test (1)
Contextually to the previous step the CI carries out all the tests. A special attention is about how
to carry out functional tests.

## Initialize library
In this phase the signing keys are generated by the license generator executable (`lccgen`), and
optionally the source code of the library may be modified or obfuscated.

## Integrate into the product
The source code of the library can and should be manually altered to prevent hackers from finding a
single cracking mechanism for all the products that integrate the library.

## Deliver the product to the client
The compiled product is delivered to the client.
 * If we want to link the execution to a specific hardware we need to send the product to the client
   without a license (or a demo executable, with the sole intent to generate the machine
   identifier).
 * If we just want to send a demo product with an expiry date we prepare a license without the
   machine identifier.

## Build process
From the process described above, (strange to say) the license generator (`lccgen`) configures
itself as a build dependency of the licensing library, thus it needs to be built first.
